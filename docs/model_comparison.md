## What this actually shows

**The column that matters is the last one, and it is zero in every row.**
Across a strong model, a degraded model, a deliberately naive heuristic, and no
investigator at all, the amount of money falsely auto-closed is INR 0.00. That
is the claim the architecture is making, and this table is the only evidence
here that tests it against something other than a single investigator.

**The strong model wanted to close every adversarial case.** `gpt-oss-120b`
proposed a resolvable hypothesis on **6 of 6** wrong-linkage cases and asked to
resolve. It was not hedging or confused — its reasoning was fluent and specific,
and it was wrong six times out of six. The Evidence Gate rejected all six on
linkage. Without the gate, that row reads *six false auto resolutions*.

**The highest scoring investigator is the dumbest one, and that is a warning,
not a finding.** The offline stub scores 100% because this dataset's ambiguity
is precisely the shape its one heuristic assumes: find an unlinked refund whose
amount equals the shortfall. It is not competent, it is well-matched to the
fixture. Anyone reading the stub row as "the best model" has read it backwards —
it is the clearest available demonstration that *headline accuracy on synthetic
data is close to meaningless*, which is why false auto resolutions and rupee
exposure are the reported headline instead.

**Gemini's row is a rate limit, not a capability measurement.** 13 of its 15
investigations returned HTTP 429 (free-tier daily quota exhausted) after four
retries each, honouring `Retry-After`. Those 13 degraded to
`HUMAN_REVIEW_REQUIRED`. That is the intended failure direction — the system
became *unproductive*, never *wrong* — but its 90.6% must not be read as a
judgement about the model. On the two cases it did complete it behaved sensibly,
and it twice offered the payment's own id as refund evidence, which the
admissibility filter dropped before the gate saw it.

**NVIDIA (`meta/llama-3.3-70b-instruct`) was configured and works** but averaged
~60 seconds per investigation with repeated rate-limit retries, so a full pass
exceeded 20 minutes. It is excluded from this table for wall-clock reasons only,
not for quality. `LEDGERGUARD_PROVIDER=nvidia` runs it.

**Cerebras is wired up but the available key returns HTTP 402** (`payment
required`), so it could not be measured at all.

## OmniRoute, and a routing trap worth knowing about

[OmniRoute](https://www.npmjs.com/package/omniroute) is a *local* router (an
`omniroute` CLI on `http://localhost:20128/v1`, not a hosted service) that fronts
~1,120 model routes behind one OpenAI-compatible endpoint. It is wired up as the
`omniroute` preset, and because auto-detection cannot tell a configured key from
a running process, selecting it first probes the local endpoint for
reachability.

It is the only available path to Claude here, since no direct Anthropic key
exists. `openrouter/anthropic/claude-opus-5` **does** work through it — verified,
with the response reporting `served: anthropic/claude-opus-5` — but the upstream
OpenRouter credential in this install deactivates after a handful of calls
(`No active credentials for provider: openrouter`, HTTP 404) and only
intermittently recovers. Two full benchmark attempts completed 1 of 15
investigations each before the credential dropped. **Claude therefore remains
unmeasured**, and no Claude column is published, because publishing a 1-of-15 run
as a model measurement would be worse than publishing nothing.

The other routes in this install are not usable either: `auto/*` resolves to slow
free models (~77–167s per investigation, mostly returning unparseable JSON),
`oc/*` returns 401, `tllm/*` 403, `ddgw/*` 418, `pepper/*` 502.

### The trap

`auto/claude-opus` **is not Claude.** Asking for it returned a response whose own
`model` field read `gemini-3.1-flash-lite`. Alias routes resolve to whatever
upstream happens to be live, so the model that answers can be a different vendor
entirely from the one named in the request.

That is exactly the class of unverified claim this whole project is about, so the
provider was changed to record the **served** model from the response envelope
rather than the requested route, and to track any divergence. On a run whose
purpose is to state which model produced a number, attributing a result to the
wrong model would have been the most embarrassing possible failure.

## Run-to-run variance

Three separate `groq` runs on the identical frozen holdout resolved **5, 6 and 7**
of the 9 F3 cases, giving 95.3%, 96.5% and 97.7% disposition accuracy — at
`temperature: 0`. Model output is not reproducible in the way the rest of this
system is, and a single headline accuracy figure from one model run should be
treated as a sample, not a measurement.

What did *not* vary across those three runs: false auto resolutions (0 every
time), value falsely auto resolved (INR 0.00 every time), and abstention on all
six F6 cases. The variance lands entirely in how much the system safely closes,
never in whether it closes something it should not have. That asymmetry is the
design working — the deterministic layer is what is stable, and the model only
moves recall.

## Reading the F3 row

No investigator resolved all 9 F3 cases except the stub. The models left 2–4 of
them for a human. Those are *unnecessary abstentions* — safe, but a missed
opportunity, and they are counted and reported separately from correct
abstentions precisely so the cost of caution stays visible.
