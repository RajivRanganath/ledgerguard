# Investigator comparison

Generated by:

```bash
LEDGERGUARD_NO_CACHE=1 python -m ledgerguard.evaluation.model_comparison \
  --providers groq,gemini,nvidia,omniroute,stub
```

Raw artifacts: `evaluation/outputs/model_comparison.{md,json}`.

Everything except the investigator is held constant: same frozen holdout (85
lifecycles), same deterministic engine, same Shadow Ledger, same Evidence Gate,
same safety gate. The only variable is which investigator proposes hypotheses.
`LEDGERGUARD_NO_CACHE=1` is required — see *Caching* below.

All four providers in the automatic chain are represented, each on its own free
tier. The **served** model is reported, not the requested one: Groq rotated to
`gpt-oss-20b` and OmniRoute to `mistral-medium-3-5` mid-run when their first
routes hit quota, and the table says so rather than crediting the route that was
asked for.

Reading the two F6 columns: *asked to close* counts cases where the investigator
proposed a real hypothesis **and** set `recommended_action: "resolve"`. *Gate
rejected* counts every case the gate positively disproved, which also includes
cases where the investigator proposed the wrong refund but only asked for review.
The two numbers come apart — NVIDIA asked to close four and the gate disproved
five — because proposing the wrong refund is disprovable whether or not the
investigator had the confidence to ask for closure.

## What this shows

**The last column is the point, and it is INR 0.00 in every row.** Across four
vendors on four separate free tiers, a deliberately naive heuristic, and no
investigator at all, nothing was ever falsely closed. That is the claim the
architecture makes, and this is the only table here that tests it against more
than one investigator.

**Every model wanted to close cases it should not have.** Groq asked to close
**6 of 6** wrong-linkage cases. Gemini asked for **5 of 6**. Mistral and NVIDIA
asked for **4 of 6** each and proposed the wrong refund in cases they only sent
to review. None of them were confused or hedging — the reasoning was fluent,
named the right refund, cited the right amount, and correctly observed that
applying it balances the ledger. Every one of those observations is true; the
conclusion is still wrong, because the refund belongs to another customer. The
gate rejected all of them on linkage. **Without the gate, the top-scoring model
in this table would still have made five silent false closures.**

**Being better at the task and being safe are not the same axis.** Gemini scores
highest at 100% *and* asked to close five of the six adversarial cases. NVIDIA
scores lowest at 95.3% *and* is among the most cautious. Ranking investigators by
accuracy would pick the one that leans hardest on the gate — which is precisely
why accuracy is not the headline here.

**The offline stub ties for first, which is a caution about the dataset, not a
result.** It reaches 100% because this fixture's ambiguity is exactly the shape
of its one rule: find an unlinked refund whose amount equals the shortfall. It is
well-matched, not competent. If a 40-line heuristic ties a frontier model,
headline accuracy on this data means very little — which is why false auto
resolutions and rupee exposure are the reported headline instead.

**Gemini needed the admissibility filter 14 times.** It repeatedly offered the
payment's own id alongside the refund id. Those ids were dropped before the gate
saw them. One of its investigations returned 429 and degraded to
`HUMAN_REVIEW_REQUIRED` — unproductive, never wrong. Every provider except the
stub needed the filter at least once.

**Latency does not track quality, and quota rotation dominates it.** Gemini and
Mistral are fastest at p50 ~2s and ~1.7s; Groq is slowest at p50 13.8s, because
its first route ran out of quota mid-run and the rotation moved it to
`gpt-oss-20b` while retries counted against the clock. Gemini's p95 of 33.9s is
one rate-limited call, not typical behaviour. All figures are free tier with
rate-limit retries included, so none are representative of a paid tier — which is
the point: this is what the system does on the infrastructure it actually runs
on.

## Caching

OmniRoute caches `temperature: 0` requests: it returns
`x-omniroute-cache-hit: true`, serves an identical response id, and does **not**
honour `Cache-Control: no-cache`. An earlier full benchmark through it returned
**15 of 15 investigations from cache at ~6ms each** — which would have been
published as model latency and as an independent second run.

The provider now counts cache hits and the benchmark prints them.
`LEDGERGUARD_NO_CACHE=1` omits `temperature` to force real calls, at the cost of
deterministic sampling, and every number on this page was produced with it set.
**The canonical benchmark runs against a non-caching provider** — the fallback
chain is the runtime resilience mechanism, not the measurement path.

## Providers not in this table

**Free tiers only.** Every investigator measured here runs on a free tier, and no
paid API key is used anywhere in this project. That is a scope decision, not a
gap: the claim is that the Evidence Gate holds regardless of investigator
strength, and four ordinary free models test that better than one expensive one.

| Provider | Why not |
|---|---|
| Anthropic (`claude-opus-5`) | Paid API — out of scope. `AnthropicProvider` is kept as the reference implementation of the provider interface and is never called. |
| Claude via OmniRoute | `oc/*` returns 401 despite the upstream showing connected; `openrouter/anthropic/*` reports `No active credentials`. Removed from the rotation rather than left in to fail. |
| Cerebras | HTTP 402, `payment required`. Excluded. |
| NVIDIA NIM | ~~Not provisioned.~~ **Resolved** — a replacement key works. See "NVIDIA, and why a model list is not an entitlement list" below. |

## A routing trap worth knowing about

`auto/claude-opus` on OmniRoute **is not Claude**. Asking for it returned a
response whose own `model` field read `gemini-3.1-flash-lite`. Alias routes
resolve to whatever upstream is live, so the model that answers can be a
different vendor from the one named in the request.

That is exactly the class of unverified claim this project is about, so the
provider records the **served** model from the response envelope rather than the
requested route, and the fallback chain keys its `served_by` counts on the model
that actually answered. Every provider-attributed number in this repository is
the model that answered, not the one that was asked for.
